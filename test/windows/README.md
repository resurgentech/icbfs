# Windows/WinFsp test environment

Everything here was actually run on this host, not just planned — see
`../../TESTING.md` for how this fits into the overall certification plan.
The end goal is running [winfsp-tests](https://github.com/winfsp/winfsp/wiki/WinFsp-Testing)
(`--external` mode) against icbfs's own WinFsp driver, which doesn't exist
in this codebase yet (see `ARCHITECTURE.md`/`ROADMAP.md` in the main repo)
— so step 5 below is still blocked. Everything before it is verified,
hands-off, and reusable right now.

## Layout

- `autounattend.xml` — the Windows Setup answer file. Tracked in git; it's
  small and it's the actual artifact that makes this unattended.
- `lib.sh` — shared config (VM name, password, SSH helper). Not run
  directly.
- `build-answer-iso.sh`, `create-vm.sh`, `wait-for-ssh.sh`,
  `check-eval-expiry.sh`, `destroy-vm.sh` — the actual workflow, as real
  scripts instead of commands copied out of prose.
- `work/` — gitignored. Large install media and generated ISOs live here;
  everything in it is either downloaded by hand once or regenerated by
  the scripts above.

## One-time setup: get the Windows ISO

The **only manual step in this entire flow.** The Windows Server 2025
eval ISO is not a direct download — Microsoft gates it behind a genuine
HTML registration form (name/email/company) on `info.microsoft.com`, not
a curl-able redirect. Register once at
[the Evaluation Center](https://www.microsoft.com/en-us/evalcenter/evaluate-windows-server-2025),
download the ISO, and pass its path to `create-vm.sh` below. (The
`virtio-win` driver ISO, by contrast, *is* a direct, gate-free download
from `fedorapeople.org` — but this VM doesn't need it, see "Why BIOS/MBR
and no virtio" below.)

## Normal workflow

```
./create-vm.sh /path/to/windows-server-2025-eval.iso
ip=$(./wait-for-ssh.sh)
./check-eval-expiry.sh "$ip"
ssh Administrator@"$ip"   # password in lib.sh
```

`wait-for-ssh.sh` auto-restarts the VM (up to 6x) if it gets shut off
before reaching SSH — see "The unexplained `libvirtd` kill" below for why
that's there.

Once you're satisfied with the VM's state:

```
virsh snapshot-create-as icbfs-winfsp-test clean-base "description"
virsh shutdown icbfs-winfsp-test   # frees its 8GB; the snapshot keeps the state
```

To reuse it later: `virsh start icbfs-winfsp-test`, then
`./wait-for-ssh.sh` again (it's already installed, so this is fast).

To tear it down entirely: `./destroy-vm.sh`.

## Why BIOS/MBR and no virtio drivers

This host's `win2k25` libvirt/osinfo profile defaults to SeaBIOS, not
UEFI (confirmed by the absence of a `<loader>` tag in the generated
domain XML), so `autounattend.xml`'s `DiskConfiguration` uses simple MBR
partitioning, not a GPT/ESP/MSR layout. And since the VM uses an emulated
SATA disk and e1000e NIC (not virtio), Windows Setup sees them natively —
no driver injection needed at all, which keeps the unattended install one
step simpler. `virt-install --os-variant win2k25` auto-applies the
correct Hyper-V enlightenments and `cpu mode="host-passthrough"` on its
own; nothing extra to configure there either.

## What went wrong building this (kept on record, not just the happy path)

- **First real problem**: the VM installed, then sat at a `logonui.exe`
  "press Ctrl+Alt+Del to unlock" screen indefinitely. Root cause: the
  OpenSSH-enablement commands were under `FirstLogonCommands` in the
  `oobeSystem` pass, which only fire on an actual interactive logon —
  without an `<AutoLogon>` block, nothing ever logs in to trigger them.
- **First fix attempt was wrong, and failed loudly.** Moved the commands
  to `RunSynchronousCommand` in the `specialize` pass instead (runs as
  SYSTEM during setup, no logon needed). That traded one bug for a worse
  one: `specialize` runs very early, before networking is reliably up,
  and **any** non-zero exit from a `RunSynchronousCommand` there aborts
  Setup outright with "The computer restarted unexpectedly... Click OK to
  restart the installation" — hit that for real, on a fresh install,
  confirmed via `virsh screenshot`. `FirstLogonCommands` doesn't have that
  failure mode (a failing command there doesn't nuke the whole install).
- **Correct fix** (what `autounattend.xml` does now): stay with
  `FirstLogonCommands` in `oobeSystem` and just add the missing
  `<AutoLogon>` block so a human never has to trigger it — plus
  `-ErrorAction SilentlyContinue` and a forced `; exit 0` on every
  command, belt-and-suspenders against this exact class of failure
  recurring.
- **The unexplained `libvirtd` kill — mitigated, not solved.**
  Independent of the answer-file bugs above, this VM's
  `qemu-system-x86_64` process was killed mid-install by a direct
  `SIGTERM` from `libvirtd` itself (confirmed in
  `/var/log/libvirt/qemu/icbfs-winfsp-test.log`:
  `terminating on signal 15 from pid 1067 (/usr/bin/libvirtd)`) —
  multiple times, at different elapsed durations each time (not a fixed
  timer), with `libvirtd` never having restarted. Ruled out: kernel
  OOM-kill, `systemd-oomd` (active, zero log entries), `libvirt-guests`
  (disabled), host suspend (this is a desktop, no battery, no suspend
  events in `logind`), hook scripts (`/etc/libvirt/hooks/` doesn't exist),
  wrapper binaries around `virsh`/`qemu-system-x86_64`, and any extra
  watchdog process in `ps aux`. **Root cause not found.** Mitigated, per
  Jared's direction, with the auto-restart loop in `wait-for-ssh.sh`
  instead of requiring a person to notice and restart it. Worth
  root-causing separately if it keeps happening.
- **Confirmed fully hands-off** after the `AutoLogon` fix: destroyed and
  recreated the VM from scratch. It hit the `libvirtd`-SIGTERM issue once
  more (auto-restarted automatically, no human involved), then reached
  SSH with zero manual steps — no login, no intervention. Verified
  with a real SSH session, not just a port check:
  ```
  $ ssh Administrator@<winvm-ip>
  PS C:\Users\Administrator> whoami
  win-b455ggnmnur\administrator
  PS C:\Users\Administrator> Get-Service sshd | Format-List Status,StartType
  Status    : Running
  StartType : Automatic
  PS C:\Users\Administrator> Get-WindowsCapability -Online -Name OpenSSH.Server~~~~0.0.1.0 | Format-List Online
  Online : True
  ```

## The eval clock: checking whether a snapshot is still usable

The eval ISO is time-bombed (180 days). Don't track this by computing
"180 days since creation" yourself — Windows' own licensing service
(`slmgr`) already knows the real expiration, including any rearms already
used, and is the authoritative source:

```
./check-eval-expiry.sh <vm-ip>
```

Confirmed live (2026-10-10): `Windows(R), ServerStandardEval edition:
Timebased activation will expire 4/8/2027 12:08:21 AM` — so the
`clean-base` snapshot taken that day is good until **2027-04-08**.
`slmgr /dlv` (not wrapped in a script here, just
`ssh_vm <ip> 'cscript //nologo C:\Windows\System32\slmgr.vbs /dlv'`) gives
the longer form, including `Remaining Windows rearm count: 1` — one
`slmgr /rearm` + reboot is available to reset the 180-day clock a second
time (total ~360 days of life) before a from-scratch reinstall is
mandatory.

Decision rule:
- **Comfortably in the future**: just use it.
- **Close to expiring, rearm not yet used**: `slmgr /rearm` + reboot once,
  then re-snapshot `clean-base` with the new expiration noted here.
- **Expired, or rearm already used**: `./destroy-vm.sh` and
  `./create-vm.sh` again — fully unattended, so this isn't a big deal when
  it's actually needed.

## Installing real client software: WinSCP, verified end to end

Confirms this VM can host a real third-party Windows client tool the same
way the Linux side plans to use real `scp`/`rsync`/`git`, not just that
the OS itself boots and takes SSH. Actually run, not asserted:

1. **Found the real download, not a guessed URL**: probed
   `winscp.net/eng/download.php`, found the current version redirects
   through to WinSCP's official SourceForge distribution. Downloaded on
   the host, verified `file` reports a genuine `PE32 executable ... (GUI)`
   at the expected size (12,244,608 bytes).
2. **`scp`'d the installer onto the VM** — itself a real exercise of the
   "SCP client against this box" path that's the whole point of this
   environment:
   ```
   scp winscp-setup.exe Administrator@<winvm-ip>:C:\Windows\Temp\winscp-setup.exe
   ```
3. **Silent install over SSH**, no GUI/console needed (WinSCP's installer
   is Inno Setup-based):
   ```powershell
   Start-Process C:\Windows\Temp\winscp-setup.exe `
     -ArgumentList '/VERYSILENT','/NORESTART','/SUPPRESSMSGBOXES','/ALLUSERS' -Wait
   ```
   Confirmed installed by checking for `WinSCP.com` under
   `C:\Program Files (x86)\WinSCP\`, not by trusting the installer's own
   exit code (which came back empty over this particular SSH/PowerShell
   path — a formatting quirk, not a real signal either way).
4. **Real SFTP round trip using `WinSCP.com`'s scripting interface**,
   connecting back to this same VM's own OpenSSH server (`localhost`):
   ```
   WinSCP.com /command "open sftp://Administrator:<password>@localhost -hostkey=*" `
     "put C:\Windows\Temp\winscp-probe.txt ./winscp-probe-uploaded.txt" `
     "get ./winscp-probe-uploaded.txt C:\Windows\Temp\winscp-probe-downloaded.txt" `
     "exit"
   ```
   `Authenticated.` / `Session started.`, upload showed `25 B ... 100%`,
   and `Compare-Object` between the original and round-tripped file came
   back with **zero differences** — a genuinely byte-identical SFTP
   upload/download round trip through a real third-party client, not a
   port check.
5. **One real, minor gotcha found**: `ls ./somefile.txt` on a single file
   (not a directory) failed with `Bad message (badly formatted packet)`
   against Windows OpenSSH's SFTP server — a WinSCP/Windows-OpenSSH SFTP
   quirk, unrelated to the upload/download path itself, which worked
   fine. Avoid `ls`-ing a bare file path; list the containing directory
   instead if that's ever needed.
6. **`clean-base` snapshot updated** to include this install, so reusing
   the snapshot going forward starts with WinSCP already present —
   verified again with `slmgr /xpr` before re-snapshotting, no change to
   the expiration date from doing this.

Not yet possible, and not the point of this step: pointing WinSCP at
*icbfs* itself. That's still blocked on the WinFsp driver existing in the
main codebase — this section only proves the VM/tooling side of that
future test is ready.
